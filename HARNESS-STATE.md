## What This Document Is

This document describes Armature, an agent execution harness built from the ground up to orchestrate AI agent teams doing real work. It covers why I built it, what research it draws from, how it works, where it currently stands, and — most practically — how to use it when forming agentic teams for automation, research, or decision-support tasks.

## The Problem: Agents Are Engines Without Cars

When engineers reach for an LLM to automate something complex, they almost always write the same boilerplate: a loop that calls the model, parses its output, handles failures, logs what happened, and moves to the next step. This scaffolding — the while-loop, context manager, tool dispatcher, state keeper, and safety enforcer — is the real engineering work. The model itself is interchangeable.

The industry calls this scaffolding a **harness**. Frameworks like LangChain, CrewAI, and LangGraph provide building blocks, but they require a human architect to assemble them into a working system for every new use case. That's slow, inconsistent, and doesn't learn from itself.

Armature ships as a **ready-to-run harness** that executes workflow definitions written in a structured YAML format. You provide the goal; the harness handles orchestration, quality control, failure recovery, observability, and optimization.

The analogy: the LLM is the engine. Armature is the car.

## Research Foundation

Armature synthesizes four papers published in early 2026, all converging on the same insight: **the harness is more important than the model.**

### Paper 1: Natural-Language Agent Harnesses (NLAH)
**Tsinghua University, March 2026** — arXiv:2603.25723

The paper that defines the architectural model. NLAH establishes that workflows defined in structured natural language outperform equivalent code-based harnesses on complex benchmark tasks (47.2% vs. 30.4% on OSWorld). The key finding: when the harness is readable and editable text, the entire system — including an optimizer — can reason about it.

NLAH specifies seven harness components: Contracts, Roles, Stages, Adapters, State, Failure Taxonomy, and File-backed State. Armature implements all seven. The paper also defines IHR (Implicit Harness Rating), a composite quality metric used to score run quality objectively.

### Paper 2: Meta-Harness — Automated Optimization End-to-End
**Stanford University, March 2026** — arXiv:2603.28052

The paper behind Armature's optimizer. Meta-Harness introduces an outer optimization loop where a frontier model reads execution traces from prior runs and proposes improvements to the harness spec itself. The critical finding: giving the optimizer access to full execution traces (not just pass/fail scores) improves accuracy from 41% to 57% on benchmark tasks. The optimizer reasons causally about why runs succeeded or failed and proposes targeted edits.

Armature's current optimizer implements this pattern (propose → evaluate → A/B test) and will grow into the full multi-iteration, history-aware version described in the paper.

### Paper 3: AutoHarness — LLM-Synthesized Harnesses
**February 2026** — arXiv:2603.03329

AutoHarness demonstrates that LLMs can write their own harness code through iterative refinement — producing harnesses that outperform larger models without harnesses. The insight most applicable to Armature: the concept of a **harness-as-verifier**, where the harness validates that agent outputs meet domain-specific legality constraints before accepting them. This is the conceptual ancestor of Armature's judge/RaaS role.

### Paper 4: AgentSpec — Runtime Enforcement for Safe Agents
**March 2025** — arXiv:2503.18666

The safety paper. AgentSpec introduces a declarative rule language for constraining agent behavior at runtime: "before this tool call, if this condition is true, stop/ask/correct." The rules are composable, lightweight (sub-millisecond evaluation), and can themselves be generated by LLMs. Armature's lifecycle hook system implements the core enforcement architecture, with the declarative rule DSL identified as the next evolution.

## Architecture Overview

### The Nine Core Components

Every production harness must implement all nine of these. Armature ships them all.

| # | Component | What It Does | Armature Implementation |
|---|-----------|-------------|------------------------|
| 1 | **Iteration Loop** | The core while-loop: assemble context → call model → dispatch tool → update state → check termination | `DAGExecutor` + async stage runner |
| 2 | **Context Management** | Decides what to keep, summarize, or drop as context grows | `ContextManager`, prompt assembler pipeline |
| 3 | **Tools, Skills, Registry** | Primitives (file I/O, HTTP, shell) and higher-level skills (SLM/LoRA, RAG, RaaS) | `ToolRegistry`, `BuiltinSkills` |
| 4 | **Subagents** | Fan out work to child agents with isolated context and focused roles | `SubagentNode`, child harness instantiation |
| 5 | **Built-in Skills** | Non-negotiable out-of-box capabilities: retrieval, deliberation, trace submission | SLM/LoRA, RAG, SLM/LoRA skills bundled |
| 6 | **Session Persistence** | Append-only event log so runs survive crashes and can be resumed | `SessionLog` (JSONL), `ArtifactStore` |
| 7 | **Prompt Assembly** | Assembles system prompt from static prefix + spec NL + dynamic context | `PromptAssembler`, Jinja2 templates |
| 8 | **Lifecycle Hooks** | Pre/post-stage injection points for policy, logging, cost tracking | `HookRegistry`, `HookDecision` |
| 9 | **Permissions and Safety** | Tool permission levels, destructive action interception, human approval gates | `PermissionChecker`, `HumanGateNode` |

### The Four Agent Role Types

Every stage in a workflow declares one of four roles. The harness enforces distinct behavioral contracts for each.

| Role | Model Tier | Behavioral Contract |
|------|-----------|---------------------|
| `worker` | Small/medium SLM (Qwen, Gemma) | Structured execution, tool calls. Output schema enforced via guided decoding. 80–90% of task volume runs here. Cheap and fast. |
| `orchestrator` | Frontier (Claude Opus) | Multi-step planning, routing decisions, coordinating across workers. Knows the full workflow state. |
| `judge` | Frontier | Quality scoring, evaluation, RaaS deliberation. The only role that can block a workflow from advancing. |
| `researcher` | Frontier or large | RAG synthesis, complex reasoning over retrieved context. |

The harness automatically escalates: if a worker stage fails schema validation or produces low-confidence output, it re-routes to the next model tier and retries. This happens without any workflow author intervention.

### How a Workflow Is Defined

Workflows are YAML files. A stage might look like this:

```yaml
stages:
  - id: analyze_request
    role:
      type: worker
      model_tier: small
      description: |
        Parse the incoming customer request. Identify intent, extract entities,
        flag ambiguity. Return structured analysis.
    output_mode: guided_json
    output_schema:
      type: object
      required: [intent, entities, ambiguity_score]
      properties:
        intent:    { type: string }
        entities:  { type: array, items: { type: string } }
        ambiguity_score: { type: number }
    on_fail:
      loop: { max: 3 }          # retry up to 3 times with error context injected

  - id: draft_response
    depends_on: [analyze_request]
    role:
      type: orchestrator
      model_tier: frontier
      description: |
        Draft a response to the customer using the analysis. Be concise.
        If ambiguity_score > 0.7, ask one clarifying question instead.
    output_mode: guided_json

  - id: quality_check
    depends_on: [draft_response]
    gate: human                  # pause here for human approval before sending
```

The workflow author writes natural language descriptions of what each stage should do. The harness handles everything else: routing to the right model, enforcing the output schema, retrying on failure, recording the trace, and handing off to the next stage.

### The Self-Improvement Loop (Four-Loop Flywheel)

This is the strategic differentiator. Each loop makes the others more effective.

```
                        ┌─────────────────────────┐
                        │   Armature Harness        │
                        │  (executes workflows)     │
                        └────────┬────────────────┘
                                 │
              records every run to TraceStore (SQLite)
                                 │
                    ┌────────────▼───────────────┐
                    │   Loop 1: Harness Optimizer │
                    │   Reads traces → proposes   │
                    │   YAML spec improvements →  │
                    │   A/B tests against IHR     │
                    └────────────┬───────────────┘
                                 │ accepted diffs
                    ┌────────────▼───────────────┐
                    │   Loop 2: SLM           │
                    │   High-quality traces →     │
                    │   LoRA fine-tune SLMs →     │
                    │   register as model tier    │
                    └────────────┬───────────────┘
                                 │ better workers
                    ┌────────────▼───────────────┐
                    │   Loop 3: RAG 
                    │   Trace failures reveal     │
                    │   knowledge gaps → improve  │
                    │   retrieval index           │
                    └────────────┬───────────────┘
                                 │ richer context
                    ┌────────────▼───────────────┐
                    │   Loop 4: RaaS            │
                    │   Calibrate deliberation    │
                    │   priors from outcomes →    │
                    │   cleaner quality signal    │
                    └────────────────────────────┘
```

**The key property:** the harness gets measurably better the more it runs — without any human engineering effort after initial deployment. Traces fuel fine-tuning. Fine-tuned models produce better traces. Better traces improve the optimizer's proposals. Better specs produce better traces.

## How to Use This Harness When Building Agentic Teams

This section is practical guidance for anyone forming a team of AI agents to do real work.

### The Mental Model: Teams Have Roles

Every effective agentic team follows the same four-role structure Armature enforces:

- A **worker** (or several) does the actual labor — processing data, generating content, writing code, making API calls. Workers are fast, cheap, and guided by strict output schemas.
- An **orchestrator** manages the overall task — decides what to do next, routes to the right worker, handles exceptions, maintains the big picture.
- A **judge** validates quality — checks that worker outputs actually solve the problem before the workflow advances. Without a judge, bad outputs propagate silently.
- A **researcher** enriches context — retrieves relevant information from external sources (documentation, databases, prior work) to improve worker and orchestrator performance.

Most simple workflows need only workers and a judge. Complex workflows add an orchestrator. Knowledge-intensive workflows add a researcher.

### Step 1: Define the Workflow as a YAML Spec

Start with the stages. Ask: "What does this team need to do, in what order, and what does each step produce?"

A customer support triage team might look like:

```
[researcher: retrieve customer history]
         ↓
[worker: classify intent and urgency]
         ↓
[judge: validate classification quality]
         ↓  (if quality < threshold, retry with enriched context)
[orchestrator: decide routing — escalate, auto-reply, or queue]
         ↓
[human gate: approve if escalating to senior support]
         ↓
[worker: draft response or ticket]
```

Each stage gets a natural-language description of what it should do, an output schema (what it must produce), and an optional failure recovery policy. This is enough for the harness to run it.

### Step 2: Assign Models to Tiers, Not to Stages

Do not hard-code a specific model (e.g., "claude-opus-4-7") to a specific stage. Instead, configure model tiers in the spec and let the role type determine routing:

```yaml
model_tiers:
  small:    { provider: ollama, model: qwen2.5:7b }     # local, near-zero cost
  medium:   { provider: openrouter, model: qwen3.5-72b } # fast, moderate cost
  frontier: { provider: anthropic, model: claude-opus-4-7 } # best quality
```

Workers default to `small`. Judges and orchestrators use `frontier`. The harness escalates automatically when quality falls short. This means:
- 80–90% of your token spend stays on cheap local models
- Frontier model usage is reserved for where it matters
- You never have to think about model selection per task again

### Step 3: Add Quality Gates — Don't Skip Them

The single most common mistake in agentic team construction is omitting the judge. When workers produce outputs that feed directly into the next stage without validation, garbage propagates downstream and failures surface late and expensively.

Every workflow should have at least one judge stage. The judge uses RaaS deliberation to score output quality and block advancement if confidence is below threshold. The harness will automatically retry the failing stage (with the error injected as context) before giving up.

```yaml
  - id: validate_output
    depends_on: [worker_stage]
    role:
      type: judge
      model_tier: frontier
      description: |
        Evaluate whether the worker's output correctly addresses the user's intent.
        Score confidence 0.0-1.0. Reject if below 0.75.
    output_mode: guided_json
    output_schema:
      type: object
      required: [accept, confidence, feedback]
      properties:
        accept:     { type: boolean }
        confidence: { type: number }
        feedback:   { type: string }
```

### Step 4: Wire Observability From the Start

Every harness run automatically writes to the `TraceStore`. You don't need to instrument anything — it's on by default. After a handful of runs you can call:

```python
from armature.state.traces import TraceStore
store = TraceStore("~/.armature/runs/my-workflow/traces.db")
ihr = await store.compute_ihr(run_id)
print(f"Run quality: {ihr.ihr:.2f}")
print(f"Success rate: {ihr.success_rate:.0%}")
print(f"Output validity: {ihr.output_valid_rate:.0%}")
```

IHR (Implicit Harness Rating) is a 0–1 composite: 40% output validity, 30% stage success rate, 20% RaaS score, 10% latency score. A well-tuned workflow should score above 0.80.

When you have 5+ runs of a workflow, run the optimizer:

```python
from armature.optimizer.runner import OptimizerRunner
runner = OptimizerRunner(
    target_spec_path="workflows/my-workflow.yaml",
    trace_db_path="~/.armature/runs/my-workflow/traces.db",
    metric_fn=lambda outputs: outputs.get("confidence", 0.0),
)
result = await runner.optimize()
if result and result.accepted:
    print(result.proposed_diff)   # review and apply the suggested change
```

The optimizer reads your traces, identifies the most common failure pattern, and proposes a targeted change to the workflow YAML. You review the diff and decide whether to apply it.

### Step 5: Integrate Existing Agent Frameworks as Adapters

Armature does not replace frameworks like CrewAI, LangGraph, or AutoGen — it wraps them. If you already have a CrewAI workflow that does document analysis, you can use it as an adapter stage inside an Armature workflow:

```yaml
  - id: document_analysis
    adapter: crewai_doc_pipeline   # calls your existing CrewAI workflow
    on_fail:
      loop: { max: 2 }

adapters:
  crewai_doc_pipeline:
    type: python
    fn: "myproject.agents.analyze_document"
    args: {}
```

The Armature harness handles all the orchestration, quality control, trace recording, and observability around the CrewAI call. The CrewAI crew focuses on its task. This is the integration pattern for teams already using other frameworks.

### Reference Architecture: What Agentic Teams Look Like in Practice

**Research + Synthesis Team**
```
[researcher: retrieve from RAG] ──┐
[researcher: web search]                  ├─ parallel fan-out
[researcher: retrieve from internal KB]  ──┘
         ↓ (all three complete)
[orchestrator: synthesize findings]
         ↓
[judge: validate synthesis quality and citation accuracy]
         ↓
[worker: format and write final report]
         ↓
[human gate: approve before distribution]
```

**Autonomous Customer Support**
```
[worker: classify intent and urgency]
         ↓
[judge: validate classification — retry if confidence < 0.75]
         ↓
[orchestrator: routing decision]
    ├─ simple FAQ → [worker: auto-reply] → done
    ├─ billing   → [adapter: billing system lookup] → [worker: draft response]
    └─ escalate  → [human gate: notify senior support]
```

**Code Review and Quality Audit**
```
[worker: analyze diff for security issues]
[worker: analyze diff for performance issues]     ← parallel
[worker: check test coverage]
         ↓
[judge: score overall quality — block if critical issues found]
         ↓
[orchestrator: produce review summary]
         ↓
[worker: file GitHub comments]
```

## Technical Notes for Integration

### Python Library (recommended for new work)

```python
from armature import Harness

harness = Harness.from_spec("workflows/my-workflow.yaml")
result = await harness.run({"customer_id": "cust_123", "issue": "billing question"})
```

The harness is async. Wrap it in `asyncio.run()` or call from any async context.

### HTTP Service (for non-Python consumers)

```bash
armature serve --host 0.0.0.0 --port 8080 --specs-dir ./workflows/
```

Then from any language:
```http
POST /run
Content-Type: application/json
{ "spec": "my-workflow.yaml", "inputs": { "customer_id": "cust_123" } }

→ { "run_id": "a3f7b2d1", "status": "running" }

GET /runs/a3f7b2d1/result
→ { "status": "complete", "result": { ... }, "ihr": 0.87 }
```

### Environment Variables

```bash
ANTHROPIC_API_KEY=...          # for frontier model calls
OPENROUTER_API_KEY=...         # for medium-tier calls
ARMATURE_SPECS_DIR=./workflows # default spec location
ARMATURE_RUNS_DIR=~/.armature/runs
OTEL_EXPORTER_OTLP_ENDPOINT=... # optional: send traces to Jaeger/Grafana
```

## Summary

Armature is a production-grade agent harness built directly from the current state of research in agentic AI systems. It handles the structural engineering — orchestration, quality control, failure recovery, observability, and self-improvement — so that every team building on top of it can focus on the domain problem rather than the execution infrastructure.

The investment compounds. Every run improves the harness, every improvement improves the models, and every improved model makes the next run cheaper and more reliable. That's the flywheel, and it's running.
