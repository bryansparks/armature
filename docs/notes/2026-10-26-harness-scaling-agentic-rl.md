# Harness Scaling for Generalizable Agentic RL — structured harness diversity as a training dimension

**Date:** 2026-10-26
**Source:** arXiv:2610.29458v1, Fei Bai & Huatong Song (equal contribution; IQuest Research), Chuan Hao, Ran Tao, Jian Yang, Bryan Dai, Wayne Xin Zhao, Ji-Rong Wen (Gaoling School of AI, Renmin University of China).
Primary source: https://arxiv.org/html/2610.29458v1 (citations below are to this HTML).
**Question:** A paper that trains agent *policies* via RL across many harness configurations instead of one fixed harness — Armature is an orchestration engine over frozen hosted models, so the training layer is out of reach. What transfers is the methodology: a factorized harness taxonomy and a structured-diversity result that directly shapes the improve-revision brief. Does it move the needle?

---

## 1. What the paper is

An agentic-RL **training** paper (weights change; the harness doesn't). Thesis: most agentic RL trains "through a single fixed harness, which can lead to specialization and limited transfer" (Abstract, §1); harness diversity is a complementary scaling dimension to task/environment scaling — but only when *organized*.

**Factorized harness space (§3.1, App. A):** the harness is decomposed into five components, each with a base realization and transformations (variants generated by Opus-4.7, "each transformation targets a single component" — App. A):

- **System prompt (S):** direct instruction → product-context framing → narrative/role-based framing.
- **Tool interface (T):** original tool names/schemas → semantically-related aliases + distractor tools → opaque identifiers (lexical cues stripped) + distractors.
- **Observation (O):** raw tool outputs → + simulated infrastructure metadata (pod names, scheduling) → + structured XML-style metadata (exit code, PID, duration).
- **Context management (C):** full history → LLM compaction keeping 5 recent turns → aggressive: 3 recent turns + summarized history externalized to a file.
- **Workflow (W):** free-form execution → plan-first (explicit planning required) → plan-first + periodic progress verification every three steps.

3 realizations × 5 components = **243 configurations**, structured as a Hamming graph H(5,3) — d_H counts differing component dimensions (§3.1.1). Generalization objectives split into **in-space** (held-out configs in ℋ) and **out-of-space** (external black-box harnesses) (§3.1.2).

**Structured selection (§3.2):** a compact 18-config training set via a **strength-2 orthogonal design** — every component realization appears equally often, every *pair* of realizations co-occurs λ=2 times (N=λL²; Rao bound N ≥ 1+M(L−1)). **Locality-aware cross-harness assignment (§3.3.1):** each task gets a uniformly-sampled anchor harness plus the K−1 Hamming-nearest configs — "controlled variation within each task with broad coverage." **Multi-harness policy optimization (§3.3.2):** standard clipped PPO/GRPO over task–harness trajectories.

## 2. Results (and how much to trust them)

Trained Qwen3-4B-Instruct and Qwen3-30B-A3B-Instruct on ClawGym-Task (13.5K workspace tasks), GRPO and PPO, 300 steps, 16–32 H20 GPUs (§4.1, App. C.1). Evaluated on ClawGym-Bench (workspace agent tasks), JobBench-Easy (professional workflows), PinchBench (research/coding/scheduling/file tasks), plus **zero-shot transfer to OpenClaw and Claude Code as unseen black-box harnesses** (§4.1, App. C.2).

- **In-space:** +9.80/+3.57 (GRPO/PPO, 4B), +5.21/+4.90 (30B) over single-harness RL, averaged across benchmarks (Table 1, §4.2).
- **Black-box transfer:** beats black-box SFT (12,800 OpenClaw trajectories) and black-box RL (trained through OpenClaw) on held-out Claude Code — e.g. 4B: 37.22 vs 35.08 SFT / 33.38 RL Pass@1 (Table 2).
- **The ablation is the headline (§4.3, Table 3):** structured-18 beats random-18 (ClawGym: 52.78/45.37 vs 47.90/42.78), beats a 3-harness set, and beats **full-243 at the same budget** — training on *all* configs including eval harnesses still loses to the balanced 18. **Organization of diversity, not quantity, drives the gains** (§6).
- **K=2 is optimal** (beats K=1, same-anchor repeat-2, and K=4); random task assignment loses 2.32–3.04 points vs locality-aware (Table 10).
- **Robustness is nearly free:** generalization costs only −0.19 on the base harness while gaining +10.48 in-space and +3.60 on Claude Code (30B GRPO, Table 4). Largest capability gains: state tracking, workflow compliance, error recovery (§5.1 — judged by GPT-5.4 five-point rubric over 200 trajectories per held-out harness, App. D; reported only as normalized profiles, no numeric deltas).

**Honest weaknesses:** (1) RL training with 16–32 GPUs — a layer Armature categorically does not operate at (we orchestrate frozen hosted models); (2) the "factorized space" variants are Opus-4.7-generated — in-space generalization is partly generalization within one model's stylistic neighborhood; (3) capability gains have no numeric deltas; (4) black-box budgets only "approximately matched" (38,400 trajectory exposures, App. C.1); (5) benchmarks are workspace-task suites adjacent to the training distribution. **Naming collision:** 2610.14224 (Harness²) has a *negative baseline also called "Harness Scaling"* (naive per-task test-time revision) — same words, unrelated concept. Don't cross-reference them by name.

## 4. Relation to the other notes — a third source on controlled paired variation

The methodology now has three convergent sources pointing at the same improve-revision design:

1. **2610.30499** (self-harness note): frozen-snapshot *selection* over candidates beats last-write-wins; abstention matters.
2. **2610.14224** (Harness² note): *probe each candidate on the same task*, select on behavioral contrast, compose-or-keep.
3. **2610.29458** (this note): at training scale, the pairing should be **locality-aware** (anchor + Hamming-nearest, K=2) and the candidate pool should be **structured (balanced factorial) not free-form** — random diversity and exhaustive diversity both lose to organized diversity.

Read together: if probe-style improve is ever built, this paper supplies the *candidate-set geometry* (balanced factorial over the five dimensions, minimal-diff pairs) that Harness²'s Propose–Probe–Compose lacks. Harness² says *run and contrast*; this paper says *what to vary and how much*. The papers were written independently of each other and of Armature.

## 5. Verdict

**Shelve implementation; keep as a refinement of the improve-revision brief.** The mechanism (RL training) is at a layer Armature doesn't and shouldn't operate at — same verdict shape as the cache-engineering paper. What survives is methodology, and it sharpens an already-recorded design item rather than adding a new one: improve-brief item #2 (probe-and-contrast) should specify **balanced factorial candidate generation + K=2 locality-aware pairing** rather than free-form proposals. Also worth keeping: the harness-as-portability-boundary citation for the factory charter, and the nearly-free-robustness argument for the campaign eval suite. Discount the headline numbers as usual — Opus-4.7-generated variant space, judge-scored capabilities with no deltas, workspace-adjacent benchmarks.

**Revisit trigger:** identical to the Harness² note's item 2 — this note rides along with it, it does not open a new arc.
