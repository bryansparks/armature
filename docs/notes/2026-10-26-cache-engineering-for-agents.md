# Cache Engineering for Agents (AKV) — drop/reposition KV cache control

**Date:** 2026-10-26
**Source:** arXiv:2610.28577v1 (submitted 2026-10-20), Tianyu Fu, Ruoxi Wang, Zihan Min, Zhongqi Ren, Zhihao Li, Tengxuan Liu, Shengxuan Mu, Hanling Zhang, Yu Wang (Tsinghua & CUHK; cs.CL).
Primary source: https://arxiv.org/html/2610.28577v1 (all citations below are to this HTML). Code: github.com/thu-nics/AKV.
**Question:** A serving system that lets agents directly operate on their KV cache (drop entries from attention, reposition keys) instead of editing context text. Armature is a *client-side* orchestration engine calling hosted APIs — what, if anything, transfers?

---

## 1. What the paper is

A **serving-system + policy** paper. Problem framing (§1, §3.2): long-horizon agents accumulate trajectories past the context limit; existing *context engineering* (threshold-triggered summarization) rewrites the history prefix, which invalidates downstream cached KV and forces re-prefill of everything retained — "trim-based context engineering costs 1.85× as much as full-context" and in the full-context regime "KV cache reads take up 82.4% of the total API cost" (Fig. 14). The dilemma: edit text and pay re-prefill, or keep everything and pay cache reads.

**Thesis:** operate on the cache directly — `drop` removes selected KV entries from *subsequent attention* (token sequence unchanged), `repos` re-encodes retained positions to 0…r−1 via RoPE rotations so execution isn't halted by position limits (§3.3). Cache states become *history-dependent*, so the paper formalizes an **operation sequence** o₁:ₘ that deterministically determines cache state (§3.4) and builds **AKV**, a serving system on SGLang whose interface is "stateless interface, stateful serving": each API request fully describes its cache operations (`cache` field; §4.1). Internals: a radix tree extended with **drop nodes** so prefix matching distinguishes operation histories, drop-aware eviction, segment-batch attention for restoring missing states in one prefill pass, and reposition-aware reuse via key rotation instead of recomputation (§4.2, App. A.1.2).

## 2. Key findings

- **Rolling-drop beats summarization on both axes.** A "tool-response rolling-drop policy that retains the KV states of the latest 12 tool responses" (§5.1) vs. threshold-triggered summarization (Pi-style compaction at 96K/192K): average score **+1.7 points**, average cost **−27.7%** (−21.9% vs. 48K summarization), across 3 open-weight models (MiniMax-M2.7, GPT-OSS-120B, MiroThinker-1.7-Mini) on 4 long-horizon benchmarks (BrowseComp-Plus, GAIA-Text, SWE-bench Verified, xbench-DeepSearch) (§5.2, Table 1). Accuracy gains appear exactly in the regime where summarization bites (§5.2, Fig. 7).
- **Why dropping tool responses specifically:** attention analysis shows older *tool responses* get less attention than older *reasoning*; dropping reasoning cache scores worse than tool-only drop (Table 3; Fig. 15).
- **repos unlocks exploration past the position limit:** on BCP it lifts 55% → 62% (Table 3) by letting runs continue beyond position-encoding limits without re-encoding.
- **Serving wins:** 1.36× mean / 1.51× P95 latency speedup, 1.53× input / 1.18× output throughput at peak settings, replaying the 80 largest-context SWE-Verified trajectories (§5.3, Table 2); 59.8% less full-attention time (A.4.1).
- **Cache-As-Tool (CAT) tops fixed policies:** giving the agent a *tool* to manage its own cache beats the fixed rolling-drop policy on BCP — 61.0% (GPT-OSS-120B, also cheaper) and 64.0% (MiniMax-M2.7) (§5.4, Table 4).
- **Recursive self-improvement (RSI) of cache policies:** MiniMax-M2.7 refines the cache *policy* itself on 20 BCP tasks, evaluated on 100 held-out; iterations 3 and 6 cut per-task cost 15.6% / 17.8% vs. Standard at Standard's accuracy; 7.1% cheaper than the expert-designed rolling-drop on held-out (§5.4, Fig. 4).
- **Harness-portable:** integrated into the Pi harness, AKV is +3% over native-without-compaction and +4% over native-with-compaction (A.4.3).

## 3. Applicability to Armature

**The headline verdict: the paper's core machinery does not apply** — Armature is a client of hosted APIs (OpenRouter/Anthropic), not a serving stack. `drop`/`repos`/drop-nodes/segment-batch attention all require owning inference. Only the *policy-level* findings transfer, and Armature already owns the levers for those. Mechanism by mechanism:

| Paper mechanism | Armature status | What would transfer |
|---|---|---|
| `drop`/`repos` KV operations + AKV serving system (§3–4) | **Not applicable.** Armature has no inference stack and no KV-cache API surface on hosted providers. Anthropic/OpenRouter prompt caching is the only client-visible cache, and it exposes no entry-level operations. | Nothing now. Revisit only if Armature ever self-hosts models (the fs-aws LoRA/SLM research line is the only conceivable consumer). |
| Tool-response rolling-drop > summarization (−27.7% cost, +1.7 score) | **Partial — Armature has the policy machinery, not the policy.** `context_layers`/`context_policy` (`never:`), `signature.input` filters, and the fan-out `_transcript` guard ARE the levers; but Armature's *default* is cumulative context — every downstream stage sees all prior outputs, i.e., the paper's "full-context" regime where cache reads are 82.4% of cost. For long workflows this is exactly the H4-v2 passive-injection pain. | Policy guidance, not code: for tool-call/ReAct-heavy stages in long workflows, prefer **dropping old tool outputs from the prompt entirely** (keep latest ~N) over summarizing them — summarization costs an extra LLM call *and* (per the paper) performs worse. Armature's `never:` closures already do drop-style removal; the paper's contribution is evidence for which shape to prefer when someone reaches for summarization. |
| "Editing the prefix invalidates cached KV" (§3.2) | **Partial.** The client-side analog is hosted prompt caching (Anthropic cache_control / OpenRouter auto-caching): any byte change in the shared prefix forfeits the discount. Armature's Jinja-rendered per-stage prompts share stable prefixes (mission, layers, system) only when rendering is deterministic; volatile values (timestamps, run ids, shuffled dict order) inside a shared prefix would silently break cache hits. | A cheap, real slice: a **stable-prefix discipline** — keep `mission` + `context_layers` + role system text byte-identical across a workflow's calls and put all volatile content *after* the cached breakpoint. Nothing to build until someone measures cache-hit rates on a live campaign and finds them low. |
| Cache-As-Tool (agent-managed context beats fixed policies) (§5.4) | **External validation for the Memory Pyramid.** CAT giving the agent a tool to manage its own context is the same shape as the pyramid's P2 read-only navigation tools — agent-pulled context instead of passive injection. The paper's CAT result (top pass rates) is independent evidence that agent-managed context beats both fixed policies and full-context, which is the P2/P3 bet made after H4-v2 showed passive injection costs latency. | Nothing to build — cite it in the memory-pyramid notes as supporting evidence when the live deep run happens. |
| RSI of cache policies (policy self-improvement, dev→held-out eval) (§5.4) | **Overlaps what improve/tune does**, in a narrower domain: refine a policy on 20 tasks, evaluate on 100 held-out. Same dev/held-out discipline the ARC-AGI-3 paper (2610.30499) found missing in most self-improvement loops. | Already covered by the 2610.30499 note's held-out-split recommendation; no separate Armature work. |
| "82.4% of API cost is KV cache reads" (Fig. 14) | **Cost-model insight.** Armature's cost metering (missions, budgets) accounts tokens, not the read/write split. On Anthropic, cached-input pricing is ~10% of base — the economics behind Armature's cumulative-context design matter more as workflows lengthen. | Optional: budget dashboards could break cost into cached/uncached input to make the cumulative-context tax visible per workflow. |

**Relation to prior notes:** where 2610.30499 evaluated the *harness self-improvement* loop, this paper evaluates *context-management policy shapes* (drop vs. summarize vs. agent-managed). The two agree on one theme: cheap wins come from better *selection/retention discipline*, not more machinery. The CAT result converges with the Memory Pyramid's P2 direction (agent-pulled context) — two independent results pointing at agent-managed context over either full retention or summarization.

## 4. Honest limitations of the paper

- All three main models are **open-weight models served locally**; the API-cost claims are computed from public token prices (§5.1, A.3), not from hosted-API billing. Hosted frontier models (Claude, GPT) with provider-controlled prompt caching have different economics — the −27.7% number does not directly transfer to an OpenRouter bill.
- Benchmarks are **single-agent long-horizon loops** (100–250 steps, up to 96–192K contexts). Armature's stages are mostly short, DAG-shaped, with curated per-stage context — the regime where rolling-drop pays off (huge tool-response histories) is the minority of Armature workloads.
- No confidence intervals reported for the +1.7-point average; gains are small and the per-model spread (+1.3 to +2.1) is narrow.
- RSI refinement used only 20 tasks; the +7.1%-over-expert figure rests on that small refinement set.
- "First serving system allowing agents to directly control their caches" is plausible but unverifiable from the paper alone.

**Verdict:** ~80% of this paper is inference infrastructure Armature cannot touch; the transferable remainder is **policy guidance** — (1) prefer dropping over summarizing stale tool outputs in long tool-heavy stages (Armature's `never:`/`signature.input` can express it), (2) a stable-prefix discipline to protect hosted prompt-cache hits, and (3) an independent citation supporting the Memory Pyramid's agent-managed-context bet (CAT). None of these clear the "moves the needle past what we already have" bar today; the note's value is having the evidence on file for when a live campaign actually measures cache economics or a long tool-heavy workflow starts hurting.
